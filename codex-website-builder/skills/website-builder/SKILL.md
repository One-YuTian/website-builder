# Website Builder

仅在用户要求建站、改页、重生成或切换网站项目时执行生成流程。插件 UI 样式/配置修改不触发建站。

## 1. 严格遵循模板排版，严禁无中生有（硬约束）

* **排版严格一致**：选择某个模板后，**必须严格按照该模板原有的排版、区域划分与元素槽位进行实现**。
* **禁止臆造内容**：**严禁以“电商业务需要”、“商业完整性”等任何借口添加原模板中不存在的结构或内容**。例如所选模板没有左侧筛选侧边栏（Filter Sidebar），就绝不得擅自增加侧边栏；模板只有顶部工具条和商品网格，就只做顶部工具条和商品网格。
* **1:1 槽位真实化替换**：模板中的骨架占位（如 `span.bg-accent`、骨架图标）仅作内容槽位映射，替换为真实的业务文本、真实图片与实际价格，**不得篡改原模板的父子层级、网格列数与对齐方式**。

### 约束优先级与 Shop 接入

用户明确要求 > 所选模板实际 HTML/JS/CSS > 准确的逐模板布局契约 > 通用视觉建议。通用版心、圆角、卡片等高建议不能覆盖模板的列数、图片比例、区域、显隐、间距或按钮形态；遇冲突先换相容模板，不靠重画布局解决。

Shop 必须先读 [Shop 接入契约](references/shop-integration.md)，同时读取选定 Shop 与 Card 的完整代码；禁止只凭 Overview 或摘要重写。模板脚本中的 defaultProducts 是演示数据，替换为 SDK 查询；保留真实容器、事件、筛选/抽屉/排序/视图切换，统一 product-id 与 card-component 标签、属性和选择器。不得把所有 Shop 都写成四列、有侧栏或同一种工具条。完成时说明所用模板及实际结构核对结果，不输出虚构还原度分数。

## 2. 色彩由 AI 自主搭配，打破固定方案（视觉自由度与卡片色差）

* **自主专业审美**：色彩选择与搭配由 AI 根据品牌定位、行业特征与商品风格**自主进行专业搭配**，**严禁死板套用 SKILL 示例或固定色彩方案**。
* **页面背景与卡片必须有清晰色差**：选用页面与板块背景色时，**必须与商品卡片底色有明确区分与层次色差**，严禁卡片底色与页面底色完全相同融为一体。例如：页面/板块背景选用浅灰或中性浅底（如 `bg-slate-50`、`bg-[#f8fafc]`、`bg-[#f1f5f9]`），商品卡片选用纯白（`bg-white`）搭配精致边框；深色模式下亦须具备明暗对比，确保卡片边界清晰、立体可辨。
* **协调与可读性**：AI 自主决定的调色板（主色 Primary、辅助色 Secondary、强调色 Accent、背景 Surface、文字 Content、边框 Outline）须在 `js/app.js` 顶部的 `window.tailwind.config` 唯一定义。必须确保文字与背景满足可读对比度，强调色能准确引导核心交互。

### PC 最大内容宽度：随机整数（硬约束）

新建网站时，全站主版心最大宽度必须在 **1200–1550px（含1200和1550）** 之间实际随机选取一个整数，不固定选1200、1280、1440或1550，也不从几个预设档位中轮换。可在建站阶段使用Node的`crypto.randomInt(1200, 1551)`获得整数N；禁止让N带小数，或把“随机”理解为凭习惯选一个常用宽度。

每个新站只抽取一次，立即将`maxContentWidthPx: N`保存到`metadata_directory/website-builder.design.json`，并在`js/app.js`唯一Tailwind主题的`maxWidth.content`中应用。遵循REM规范时，按实际PC根字号换算为REM（默认16px时为`N / 16`rem），不随意取整REM导致实际PC上限偏离整数N；记录中的像素整数是校验依据。Header、主视觉文案、商品区域、各板块与Footer共用此值并保持左右对齐，不逐页抽取不同宽度，也不在浏览器每次加载/刷新时重新随机。

同一网站的后续页面、局部修改与重生成复用已记录的N；已有网站没有记录时先确认实际版心，不能仅为执行随机规则擅自改变现有布局。用户明确指定最大宽度时按其指定值执行。正文/表单可有更窄的内部阅读宽度，全幅背景可出血，但不能覆盖全站主版心上限。此规则调整全局宽度token，不改变模板列数、断点或移动端html根字号12px；移动端仍以100%可用宽度及必要安全边距适配。验证时在足以展示N的PC视口读回主容器实际最大宽度，确认对应整数N且所有共享容器一致。

## 3. 响应式与移动端适配保持完全一致（硬约束）

* **移动端列数与断点绝不擅改**：
  * 若原模板移动端（<768px 或 <640px）是**一行显示两个商品（`grid-cols-2`）**，产出时必须**完全保持双列**，严禁擅自降级成单列纵向排版；
  * 若原模板桌面端是 4 列（`lg:grid-cols-4`），产出时严格保持 4 列；Shop-02/12 的桌面是3列，必须保持3列；
  * 若原模板采用 **Swiper 轮播**（单行多商品横向滑动），产出时必须**完整保留 Swiper 结构与滑动逻辑**，严禁擅自改成静态网格平铺或垂直列表。
* **断点逻辑忠实**：完整继承模板原始的 `sm/md/lg/xl` 规则与显隐分支（如 `hidden lg:flex`），禁止另写自造媒体查询覆盖模板响应式。

## 4. 技术栈与输出规范

* **Tailwind 与原生技术栈**：布局、排版、间距、圆角与状态完全使用 Tailwind class。`tailwind.config` 只能且必须在 `js/app.js` 顶部设置，禁止创建独立配置文件。
* **取消 commerce-config.js 文件声明**：禁止单独创建或引入 `commerce-config.js`。基础电商配置（currency、locale、storageKey）统一在 `js/app.js` 顶部或初始化时声明，由 `SDK.init` 和 `APP` 直接消费，页面中严禁声明或引入该文件。
* **组件单一定名与禁止多次注册**：取消多次 `customElements.define`，严禁对同一构造函数多次定义或别名注册。全站组件必须且只能保留唯一的 `xxx-component` 命名规则（如 `header-component`、`footer-component`、`card-component`、`cart-component`），禁止注册或在模板中使用 `header-01`、`card-01`、`product-card`、`cart-01` 等旧别名；所有 HTML 页面与模板一律使用 `xxx-component` 标签。
* **灵活支持新组件生成，不僵化固定目录结构**：如果所选模板要求使用新的组件或衍生子组件，**必须按需灵活支持生成与组织，严禁死板固守预设目录结构而拒绝生成**。新组件统一创建在 `components/` 目录下，并以 `xxx-component` 规则唯一定义与挂载。
* **购物车默认抽屉，页面为例外**：新站优先复用components/cart.js抽屉组件，默认不规划cart.html。只有用户明确要求独立购物车页，或改已有page模式网站需要保留时才用page；不能因为旧示例/默认清单有cart.html就选page。不得为提高变化而随机选择购物车模式。

* **购物车与抽屉互斥原则**：`cart.js` 组件与 `cart.html` 购物车页面**严禁同时存在**，必须二选一：
  * **抽屉模式（Drawer）**：使用 `components/cart.js`（定义并注册 `<cart-component>`），点击页头购物车按钮或加购直接唤起浮层抽屉，**严禁生成 `cart.html` 页面**；
  * **独立页面模式（Page）**：使用 `cart.html` 页面，全站所有购物车入口直接跳转至 `cart.html`，**严禁创建 `components/cart.js` 组件，页面中严禁挂载 `<cart-component>`**。
* **SDK 与数据单向流**：商品唯一来源为 `js/data.js` 的 `window.productData`；查询展示走 `window.SDK`，业务持久化走 `window.APP`。组件继承 HTMLElement（Light DOM），不破坏全局样式穿透。
* **生产输出目录**：工具返回的 `directory` 就是网站生产目录，仅写运行/发布必需的 HTML、CSS、JS、组件、字体与最终图片。`js/data.js` 是网站实际消费的唯一商品运行数据，允许保留；不得再放原始数据源/导入表、样本或seed文件、抓取原文、生成脚本、草稿、提示词、源素材、多余图片版本、测试文件、日志、截图或验收报告。已有用户文件不擅自删除，发现遗留项先识别用途。
* **管理记录与过程文件**：工具返回 `metadata_directory`，位于生产目录外的 `.builder-state/projects/<project_id>/`；设计/模板绑定、文案草稿、图片生成记录、数据来源、截图与验收报告都存这里。`website_write` 对根级 `website-builder.*.json` 管理记录自动路由到该目录，不把它们发布到网站。直接文件操作时必须显式使用 `metadata_directory`，不能假设相对路径也会被路由；临时脚本/原始数据也放此目录的 work/ 子目录，完成后只复制实际引用的最终产物到生产目录。旧工具尚不返回该字段时，按 directory 上两级的 `.builder-state/projects/<project_id>/` 推导并核对路径，不在生产目录造替代记录。

## 5. 视觉与排版细节硬约束（强制遵守）

1. **禁止字符/Emoji 图标与伪造图片**：全站不得用 Unicode 字符、字母、Emoji、HTML 字符实体（如心形、星星、购物袋、箭头）充当 icon，也不得通过 CSS content 填普通字符或 Emoji 充当图标。使用已引入的一致图标库（如 Bootstrap Icons 的 bi 类）或图片图标，提供可访问名称；正常文字、数字不受限。严禁自绘 SVG、SVG data URI、CSS/canvas 画作替代商品图或 Banner；使用可加载的真实素材或图片生成技能产出的位图。缺图如实标记，不伪装完成。

   **禁止使用五颜六色的 icon**：全站图标颜色必须保持纯粹与高度克制，严禁页面中出现五颜六色、色彩杂乱的图标（Icon）；图标颜色应遵循全局主色/文字色/中性色规范，保持单色风格。
2. **原模板中文案前面没有 icon，则不要随意添加 icon**：忠实于原模板的排版与视觉表达；原模板中文案、列表项、特性点前若无图标，严禁擅自或随意添加图标（如 checkmark、bullet 图标、装饰性 SVG 等）。
3. **文案介绍中不能出现具体的数据、承诺**：文案内容严禁出现未经真实核实的具体虚构数据（如“已服务 100,000+ 用户”、“提速 99%”等）或绝对化承诺（如“100% 正品保证”、“终生保修”、“无条件包换”等）。
4. **原组件中按钮是圆形，则不要随意改为圆角矩形，如果是圆角矩形，则遵守全局圆角的大小**：按钮形态严格保真与全局统一；原模板组件中按钮若是圆形（如圆形图标按钮），严禁擅自改为圆角矩形；若是圆角矩形，必须严格遵守全站统一的全局圆角规则，不得各处大小不一。
5. **不能出现非模板要求的阴影、投影、hover 描边效果**：视觉效果克制，严禁滥用特效；严禁随意添加原模板中未声明的卡片阴影（`shadow-*`）、浮动投影以及 hover 触发的额外边框描边（如 `hover:border`、`hover:ring`）等视觉干扰效果。
6. **不能随意增加支付 Logo、社交 icon、外链**：严禁擅自增设外链与外部徽标；原模板若无相关槽位，严禁随意在页脚、结算页或任何区域添加支付渠道 Logo（Visa、Mastercard、PayPal 等）、社交媒体图标矩阵或非必要的外部链接。
8. **icon 的背景色保持样式统一，要么没有颜色，要么统一颜色**：图标容器的背景色必须全局保持一致规范，要么通体无背景色（透明背景），要么使用全局统一的背景色（如统一浅底色或同一中性色），严禁不同图标各用各的背景色。
9. **页面圆角不要过大，要么就非圆角，要么就小圆角，要么就全圆角**：页面圆角禁止过大，避免夸张不协调的圆角尺度；圆角风格在全站应统一且清晰——要么完全直角非圆角（`rounded-none`），要么微小圆角（如 `rounded-sm` / `rounded` / `rounded-md`），要么全圆角/胶囊圆角（`rounded-full`，仅限药丸徽章或特定圆形按钮）。
10. **全站版心与左右边距必须保持高度统一**：选用的模板与组件必须严格符合统一排版需求，禁止同一个页面中一个板块保留左右边距而另一个板块随意取消边距贴边展示；全站各区块容器如果有边距，**必须统一保持相同的版心与边距规格**（统一使用max-w-content居中版心与一致的移动安全边距，PC尽量px-0，避免嵌套叠加左右padding），严禁左右边距忽大忽小、参差不齐。
11. **商品卡片高度固定与文案两行省略**：同一网格或轮播中的商品卡片必须保持**完全一致的高度与布局结构**（外层 `h-full`，内容区 `flex flex-col justify-between`），标题区域文案过长时必须使用 `line-clamp-2` 截断并显示省略号，严禁因标题字数差异导致卡片高低错落。
12. **面包屑导航超长文案截断省略**：商品详情页及各页面的面包屑导航必须保持单行水平排列，商品名称或层级文案过长时必须设置最大宽度限制并使用 `truncate`（如 `truncate max-w-[180px] sm:max-w-xs`）显示省略号，严禁文案过长折行破坏单行面包屑排版。

## Codex 插件执行流程

以上是 SKILL 的创作要求；模板还原度不进行自动评分，不作为页面生成成功或 ready 的依据。80% 只保留为复用指导，不能理解为允许臆造20%的额外内容。品牌色彩和亮暗方案由Agent决定，主版心最大宽度按上方1200–1550px随机整数规则确定，再比较并选择契合的模板；不得总取候选数组第一项或固定套用同一Shop/About布局；模板选定后忠实保留其布局与响应式。

1. 提取品牌、语言、货币、商品来源、页面和交互；缺失非关键信息时合理决策，默认单语言。先读 [整站设计](references/visual-design.md)，将简短设计决策和购物车模式（新站默认drawer）保存到 metadata_directory/website-builder.design.json；单页修改复用现有系统。
2. 先调用 website_project(action="open",thread_id=当前真实会话ID,name,brief,language,pages)。同一 thread 复用同一项目；仅用户指定新项目才 new_project=true，指定已有项目才 project_id。生产产物仅在返回的 directory（插件源码 project/xxxx-xxxx-xxxx-xxxx/），过程文件只在返回的 metadata_directory，不修改来源目录。首次需要预览时调用一次 open_canvas，不重复打开。
3. **完整电商建站必须声明完整页面计划**：默认包含 index.html（首页）、shop.html（商店）、product.html（详情）、wishlist.html（心愿单）、checkout.html（结账）、login.html、register.html、about.html（关于）、contact.html（联系）、terms.html（服务条款）、privacy.html（隐私政策）、return.html（退换货政策）。默认购物车为drawer；用户明确选page或需保留已有page模式时另声明cart.html、在页面直接实现；选 drawer 时仅省略 cart.html，提供 components/cart.js，不能连带省略品牌、联系或政策页面。只有用户明确限定局部页面或功能范围时才精简；已有不同命名或合并账户页可沿用，但必须逐项核对用途，不能静默遗漏。当前项目已存在时先比较完整清单，用 plan 补充本轮缺页，不另建项目。政策/正文页没有专用模板时复用共享页头页脚与正文版式，不因没有模板而删页，政策内容依据真实业务资料，不编造承诺。完整规划后逐页生成；不得只完成首页和交易页便宣称整站完成。计划页先显示加载扫光，完整输出后独立展示；用户旧文件不自动删除。
4. 数据与 SDK 接口读 [商品与SDK契约](references/commerce-data.md)。用户提供商品JSON/JSON文件时先调用同包 [商品导入与读取](../import-products/SKILL.md) 和website_products，不直接读取源JSON。成功后复用SDK运行视图；mode:classification_required时先根据分类摘要提交category_map、完成二次分类再导入，不能直接沿用过多源分类；渲染图片时显式调用storeData.imageUrl拼接CDN，源JSON与运行图片路径均不改写。工具返回mode:mock时接续Mock Data流程并说明回退。其他已有数据/API直接复用；无商品数据时调用同包 [generate-mock-data](../generate-mock-data/SKILL.md)，主技能不负责 Mock 参数、样本扩增或生成步骤。非商品文案调用 [website-copywriter](../website-copywriter/SKILL.md)，Logo/Banner/About Us/图片图标等调用 [website-image-generator](../website-image-generator/SKILL.md)。新站必须逐项评估并充分使用这三个技能：网站文案缺失即调用文案技能；缺少所需品牌/叙事图片即调用图片技能；没有真实商品数据即调用Mock Data技能。不能只链接技能却自行草率填占位文案、伪图或重复商品；已有有效内容直接复用，避免无谓重生成。先确定槽位和图文需求，再让文案与图片技能协作，最后接入同一份商品数据。账户 register/login/update 必须 await。
5. website_templates(mode="select") 返回候选及历史使用统计usage，由Agent比较后选择相容组合，不随机决定主题、不按编号直接选第一个，也不机械禁用-01。完整新站必须比较至少3个Shop与至少3个About候选（不足3个则全看），依据真实区域、图文结构、内容长度和筛选需求作选择；在同样适合的候选中优先较少使用的不同布局。为Shop和About各保存候选、所选ID、布局理由与历史重复/例外理由到metadata_directory/website-builder.design.json，并用targets绑定实际来源以供后续统计；不得只换颜色或文案仍重复一套布局却声称多样。已有网站局部修改沿用原模板，用户要求重设计时才重新选型。批量 code 读取本轮1–12个 ids 的 Overview、HTML、JS、必要CSS，先看A/B区域表。模板ID只作来源追溯；代码实际注册/挂载统一改为 xxx-component，嵌套组件和脚本选择器同步映射，同一构造函数只注册一次。可用 targets 保存模板绑定到 metadata_directory/website-builder.templates.json，绑定不是成功条件，旧 audit 仅返回来源信息，无需调用。
6. 首次建组件读 [创建规范](references/creation-contract.md)，按 app.js配置/数据SDK → 共享组件 → 页面推进。按模板所需新增 components/ 子组件，不限制为固定几个文件。APP负责持久化，SDK查询，app编排，不能覆盖APP。
7. 遵守 [逐页落盘与代码格式](references/code-output.md)：共享依赖准备后，每完成一个页面的完整代码就立即website_write到文件并检查ready，之后才开始下一页生成；禁止先生成全站代码再统一输出。接口支持一次提交多个HTML和共享依赖，已有代码/批量导入不受单页限制；新生成页面完成即写，不人为等待全站。其他未生成页面保持queued/未完成。当前页先begin，fragment=true自动装配HTML；完整HTML/JS/CSS用fragment=false。写入链路使用插件内置本地Prettier standalone格式化（不是npm包）：2空格、printWidth 100、JS单引号/分号、LF，HTML内联JS/CSS同样格式化。语法失败不覆盖旧文件，未完整HTML不被修复为ready。直接写HTML先begin后finish；结束任务前调用finish收尾（省略paths校验所有未完成页面），检查返回状态，无页面继续处于generating；有错误则修复或明确报告。write中提交的HTML和受依赖影响的页面自动校验，不受finalize_pages空数组抑制；通过后立即ready并在UI渲染，无需等待全站或对话结束。共享代码不要绕开website_write格式化链路。
8. 完成后在375/768/1280px检查代表页的全站配色、版心/边距、卡片与背景色差、列数、轮播、图像、图标/圆角、标题/面包屑截断和真实交互。检查商品未知/空状态、筛选排序分页、购物车数量/行ID/数值金额、账户、表单/订单；失败判断 success===false。不要虚构审美/还原度分数，未实际验证时如实说明。

## 品牌、账户与商品展示补充规范

以下仅作为生成提示与创作规范，不新增工具校验、自动扫描、评分、ready门禁或统一行为拦截器。生成页面/组件时按各自职责实现，不修改现有网站来批量追溯执行。

1. **加购保持当前浏览位置**：加购物车成功后更新购物车数量/状态，可用全局Toast简短反馈；不必打开购物车，默认不自动展开cart抽屉、不跳cart页，也不把加购与打开购物车绑定。用户主动点击购物车入口时才打开所选购物车组件；用户明确要求其他交互时遵从。
2. **注册四项资料**：注册表单必须提供用户名、邮箱、手机号（带区号）、账号密码、确认密码五项，使用目标语言标签，提供明确的国际区号选择或带区号输入，按目标国家组织手机号输入；用户名不能被邮箱替代，手机号不能仅出现在结算地址表单。提交时按已有账户SDK字段接口传递和保存相应资料，异步注册及登录状态守卫继续执行。本条不新增插件端校验器，也不因这条规范批量修改SDK或现有表单。
3. **域名决定默认身份**：以用户给定或当前站点实际域名为准，去掉协议、路径、端口与www前缀后，按实际主域提取品牌名称；不能把项目随机ID、临时预览域名或文件夹当品牌。以www.abcd.com为例，默认品牌为abcd，联系邮箱为support@abcd.com，版权署名使用abcd（如© 当前年份 abcd）；跨页标题、Header/Footer、About Us、联系及政策统一使用这组身份。用户指定品牌/邮箱/版权时优先沿用。Logo可基于品牌进行符合定位的字体与视觉延展，仍使用图片。多级域名后缀按实际主域识别，不机械取倒数第二段；缺少域名且无法从上下文推断时再询问。
4. **商品详情图片不额外留边**：商品详情主图、缩略图及图片展示区域不叠加装饰性padding、空白框或额外左右外边距，尽量让图片直接贴合所属展示槽位；仍遵循整页最大内容宽度和多端布局，图文列间距保留必要层级，不为去留白裁掉商品主体，也不强制图片超出版心。源商品图片自带的空白不修改源文件。
5. **面向顾客的正式网站文案**：采用自然、具体的品牌介绍、产品相关介绍、选购引导、账户/交易提示、联系及必要政策正文，呈现正式商店语境。不得在页面、弹窗、Toast、页脚、SEO或图片文字中加入“演示网站/示例商店”“仅本地浏览器运行”“账户/收藏/购物车/订单仅为模拟”“不构成销售、收款或配送”“品牌素材为示意”等开发/演示声明，任何语言均同；不要套用用户指出的葡语告示。实现限制、Mock来源与虚构联系资料标记放在交付说明或metadata_directory，不作为店铺内容插入。真实感来自一致的品牌与具体内容，不通过虚构经营历史、认证、评价、团队、物流/收款能力或服务承诺营造；政策仍客观说明实际数据处理，不把未实现功能写成已实现。非商品内容交给文案技能，商品介绍仍依商品数据/SDK，不扩大文案技能到编造商品描述或价格。

## Logo、账户、结算与评价补充（仅SKILL规范）

本节只约束后续网站生成，不新增插件校验器、SDK校验、ready门禁、模板选型规则或自动修改已有网站。与旧提示冲突时以本节为准。

- **Logo上下边距**：在原有减少左右边距的基础上，进一步减小图片画布的上下透明/白色留白，以及Header/Footer等容器给Logo叠加的上下padding/margin。以完整有效字形边界紧凑排布，保留笔画、升降部和必要呼吸空间，不裁字、不拉伸、不通过固定高度挤压Logo。Logo仍为真实图片。
- **注册与自动登录**：注册表单包含用户名、邮箱、手机号（明确区号）、账号密码、确认密码。确认密码与密码一致；注册成功后await自动登录并核对真实登录状态，再跳转实际本站首页，忽略注册页returnTo。不把仅注册成功当成登录成功，失败须明确反馈。
- **登录后的账户导航**：Header、移动菜单及其他账户入口按实际登录状态切换。游客显示登录/注册；已登录不继续展示登录/注册菜单，改为退出登录、我的订单等适用入口。我的订单必须链接已规划并实现的页面；未实现的页面不造假链接。退出操作调用既有账户接口并刷新菜单；保留初始化、同页事件和跨页状态同步，避免短暂误显游客菜单。
- **Checkout填写与带入**：账户初始化及入口守卫通过后，自动带入当前用户已有的用户名/姓名、邮箱、带区号手机号及已有地址等适用资料；未知资料留待填写，切换账户不能残留上一用户信息。结算表单只校验必填项是否填写（trim后非空、必选项有值），不额外校验邮箱/手机号/邮编格式、长度、地区规则等；避免HTML type=email/pattern等浏览器默认校验绕过这一要求，必要时form novalidate并在页面提交逻辑仅做填写检查。此限制仅针对Checkout表单，不取消注册确认密码、登录守卫、空购物车与订单金额等业务要求。
- **Checkout优惠券与支付**：移除优惠券码入口、输入框、展开按钮和应用按钮，不新增优惠码交互。增加支付方式区域，仅显示货到付款作为可选方式，提交对应货到付款值；线上支付选项始终禁用，不展示可用线上支付入口，不加载卡号/第三方支付表单。所选模板保留线上支付项时隐藏并保持disabled，不能由用户点击、键盘或恢复旧状态重新选中。
- **订单金额下限**：结算展示、确认与提交使用同一份SDK数值金额，订单应付金额不得低于0.01。实际计算结果不足0.01时阻止提交并给出本地化提示，不伪造商品价格、运费或只抬高页面显示金额来绕过规则；错误/非数值金额同样不能下单。本条作为生成要求，不给插件或SDK增加新的校验代码。
- **库存与评价数量**：商品卡片及详情不展示具体库存数、评论总数/数量徽标，也不在按钮或星级旁附加评论计数。可按真实数据展示可售/售罄状态与评分；不得因此改写商品库存、销量或评价源数据。
- **用户评价和商家回复**：评价列表使用由用户名称首字母与稳定颜色组成的头像，显示该条真实用户评分及正文；无名称用中性字母标识，不调用图片技能生成用户头像。字母头像是本项用户指定的头像形式，不作为图标使用。已有商家回复时展示对应回复；商家头像使用网站Logo图片或省略，不冒用用户头像、不编造回复、评分或评价。长列表继续采用折叠/分页等方式控制篇幅。

## 必备交易闭环与登录门槛

网站必须实现商品浏览 → 详情 → 加购物车/加心愿单 → 购物车编辑 → 结算 → 订单确认，所有入口连接真实页面和 APP 方法，不能只做视觉按钮。仅用户明确限定功能范围时缩减。

加购与收藏前先检查 `APP.account.logged()`：未登录先展示目标语言“请先登录”提示，再跳转 `login.html?returnTo=...`；returnTo 只接受站内相对 HTML 路径，拒绝协议、双斜线、反斜线和路径越界，登录成功后返回来源页。不偷偷写入游客购物车/收藏，不先报成功，不自动重放购买动作。订单/结算页入口遵循下方状态守卫，未登录时不能沿用加购/收藏的跳登录规则。已登录的结算页还须检查非空购物车。登录/注册 await 成功结果；注册成功后自动完成登录（SDK已登录则直接复用，否则await已有登录接口），确认真实logged后跳转本站首页，不再跳登录页或returnTo。注册或自动登录失败保留可恢复输入并展示错误，不能假报已登录。

### 登录状态与页面入口守卫（硬约束）

SDK 与账户状态初始化完成后，在表单、订单数据或结算内容渲染/请求之前检查真实 `APP.account.logged()`，不能把初始化中的未知状态当成未登录，也不能仅凭本地标记或 URL 参数判断。页面职责以项目实际路由为准，覆盖订单列表、订单详情、订单确认和结算入口，不能只按某一个固定文件名判断。

* **已登录访问登录/注册页**：直接使用 `location.replace` 跳转本站首页，不展示登录/注册表单；即使 URL 带有 returnTo，也不得让该入口守卫跳往其他页面。
* **未登录访问订单/结算页**：先通过本地化 `Toast.info` 提示“未登录，请先登录”，保留约 900ms 的可见时间，再使用 `location.replace` 跳转本站首页。提示后立即终止当前页面业务初始化，不能读取/显示订单、执行结算或下单，也不能重定向到登录页。相同访问只提示一次、跳转一次。
* **未登录访问登录/注册页、已登录访问订单/结算页**：正常进入相应流程；结算继续验证购物车等业务条件。首页本身不应用这些重定向条件，避免循环。

首页路径按当前页面层级解析为本站实际首页，支持嵌套目录，不能硬编码外部域名。直接输入 URL、站内导航、浏览器返回恢复（pageshow）和账户登录状态变化后均需重新应用守卫；重入时清理旧计时器，防止退出后仍请求受保护内容或重复导航。该入口规则优先于通用 SDK 的“提示后跳登录页”默认行为；仅在入口守卫通过后调用账户/订单/结算方法，不全局改写其他页面的登录目标。

生成后实际验证：已登录分别访问登录与注册页均到首页；未登录分别访问订单与结算页均先出现提示再到首页，且无受保护请求；正常状态不误跳转。此处修改的是生成规范，不能仅修改 SKILL 后宣称已有网站已具备守卫。

内置 APP 在未登录写入时继续拒绝操作；配置 `commerceConfig.loginUrl`、`commerceConfig.loginRequiredMessage`（目标语言），SDK 默认提示并跳转。自定义 UI 可提供 `commerceConfig.onLoginRequired({code, loginUrl})` 统一显示提示和导航。既有 SDK 不覆盖，由页面显式执行同样守卫。处理 2001/3001/4001 错误，不能吞掉未登录提示。购物车行 ID、数值价格、账户隔离、订单快照遵守数据契约；下单必须防重复提交，成功才清空购物车并显示确认，失败可重试。

## 完整页面截图与验收技能

用户要求“xx 页完整图片/截图”时调用 `website_screenshot(thread_id, project_id, path, width)`；返回实际加载、字体与图片解码完成、懒加载内容展开且布局稳定后的全页 PNG，不返回画布缩略图。截图超时/缺图/页面脚本错误要报告失败，不把半渲染页面当完成。旧会话用 project.mjs 的 action:"screenshot"，返回绝对文件路径；用 Markdown 图片显示结果。

[website-acceptance](../website-acceptance/SKILL.md) 仅用户明确要求验收时调用，不自动调用。普通生成仍执行本技能的基本语法、依赖和交互检查，不宣称等同完整验收。

## 图文协作与多端图片

文案长度由实际场景决定：导航/按钮简短，Banner标题与说明精炼，About Us与隐私政策提供充分、分节、详细的内容，不在图片上硬塞长文。文案技能可按内容需要调用网站图片技能，优先选用有相应图文槽位的模板。不得编造具体数据、服务时效、保障、退款、隐私安全或其他具体承诺。

网站图片技能必须使用宿主 `imagegen`（用户所称 image_gen）技能及其内置 `image_gen` 工具，根据主体内容、实际显示尺寸、比例与留白生成最终图片。除Logo必要品牌字样或用户明确指定的图片文字外，非必要不让图片携带文案；标题、介绍和CTA放可访问、可响应式的HTML槽位。

图文排版不得遮挡图片主体、人物面部、关键物体或Logo。生成前说明主体位置和文字安全区；优先图文分栏/上下排列。模板已有叠字槽位时，仅在图片真实留白区域排文案，并逐端检查；渐变遮罩不能当作遮挡主体的理由。

优先一张高质量主图配合容器比例、object-fit/object-position或背景裁切适配PC/平板/手机，逐端保留主体与留白；不要为移动裁切改动商品网格或模板断点。只有同一图无法兼顾构图时，才生成多张适配图，以picture/source、srcset/sizes或模板现有响应式槽位正确切换，禁止仅缩小桌面图敷衍适配。生成ICON优先单色图形、透明底；需要实底时全站统一纯色，不用复杂背景、渐变或多色装饰。

在375/768/1280px检查文案换行、段落密度、图片主体与文字安全区、裁切、分辨率及加载。完整验收技能依旧仅手动调用。

## Header 必备导航

所有完整网站的Header必须同时提供Home、Shop、About Us、Contact Us四个菜单，按目标语言本地化，分别链接实际输出的首页、商品列表、关于与联系页面（默认index.html、shop.html、about.html、contact.html）。桌面导航和移动菜单都必须可访问，不能仅放页脚、只留图标、使用#空链接或在某个断点隐藏而无替代入口。即便模板演示只列商品分类，也必须在现有导航槽位填入这四项；选择足够容纳四项的Header模板，此项用户明确要求优先于演示菜单数量。改现有Header时补全四项及对应页面，保留原有合理菜单；用户明确只编辑无Header的片段时不凭空添加Header。基本检查逐一点击四项并核对移动菜单可用、链接无404。

## 移动根字号与图片Logo（硬约束）

移动端viewport宽度<768px时，必须设置html根节点font-size:12px，采用该基准计算rem；不能只给body、容器或某个组件设12px，也不能用浏览器缩放/transform缩放页面代替。在js/app.js初始化阶段、组件首轮渲染前应用，并在跨越断点时同步更新；默认桌面恢复16px或已有明确的桌面字阶规范。初始化及监听幂等，不能在不同组件各写一套根字号规则，禁止样式再次覆盖移动html为14/16px。保留模板网格、显隐和轮播断点，不因为根字号改变而改移动列数。基本检查必须读取375、767px的getComputedStyle(document.documentElement).fontSize为12px，并检查768/1280px恢复桌面值。

网站Header、Footer及移动菜单的品牌Logo必须使用真实可加载的图片，通过img或picture内的img呈现并提供品牌alt；禁止用纯文本品牌名、LOGO占位文字、首字母方块、Emoji、字符图标或自绘CSS/SVG来冒充Logo。没有用户Logo时调用网站图片生成技能生成图片Logo，检查透明度、比例、小尺寸可读性及多端显示；只把最终正式Logo文件放assets/brand。图片中必要品牌字样允许，网站标题/正文正常品牌文字不受限。

## 首页组合与不重复板块

完整首页除了Header、Footer、主轮播/主视觉、商品列表，必须按品牌内容再选择1–2个不同用途的额外板块，例如分类入口、图文品牌故事/使用场景、精选专题/促销、无虚构承诺的服务说明。优先从现有独立blocks模板中选择，再用文案/图片技能补齐真实内容；这属于首页的模板组合计划，不是往已选Shop或组件内部加区域。

两个额外板块不得复用同一个模板实例、同样的内容/视觉或同一用途，不把第二份商品列表、复制的轮播/促销Banner算作额外板块。每块应有不同信息或行动目标，避免同图同文、重复CTA和只改标题；不得为了凑数量编造评价、数据、承诺或添加支付/社交Logo。把板块顺序、用途、所选模板与不重复理由记入metadata_directory/website-builder.design.json，并在首页实际输出。用户明确指定极简/局部页面时按其范围执行，不强加整站板块。

## 预览资源异常

画布本地图片按独立资源分片加载，大页面压缩包也走分片通道。预览传输错误与网站源码生成状态分开判断：先查具体资源/传输错误，不能将画布失败等同源码生成失败，也不能仅为绕过传输限制删除图片、降质、删板块或改网站结构。正常网站仍使用生产目录相对资源路径，预览适配不改写源文件；图片体积优化依据实际性能需要进行。

## CDN与共享控件（硬约束）

所有网站字体、第三方JavaScript/CSS库、图标库使用在线HTTPS CDN，并明确版本、正确加载顺序和必要的crossorigin；禁止把第三方包、字体文件或它们的副本写入生产assets/vendor、vendor、fonts等目录，也不把库/字体Base64内嵌到网站。自有图片、组件、APP/SDK仍是项目自身运行文件，不受此CDN规则限制。只加载实际使用的依赖并全站统一版本；字体使用在线字体服务CSS，保留合理系统字体fallback。不能为绕过网络错误静默改成本地第三方副本，CDN失败通过Toast/页面错误状态说明。画布因宿主CSP通过后端代理读取这些在线URL，不改写生产网站；仅插件回归测试可显式使用隔离的固定依赖样本。

按钮、链接按钮、输入框、选择器、复选框、开关、分页、表单和Toast关闭控件使用一套全站设计语言：统一小圆角、边框、颜色、hover/active/focus-visible/disabled状态与过渡时长。按primary/secondary/ghost/danger等语义区分，不各组件随意定义不同阴影、位移、描边或圆角。圆形图标按钮继续圆形，尺寸随用途变化但状态规则一致；不把所有控件强制同一个尺寸。共享状态token/class在js/app.js的主题与window.uiStyles统一维护。此明确的全站状态样式要求优先于旧模板不一致的装饰样式，不借统一控件改网格、区域、响应式或图片比例。

## 图像细节、差异与首页去重

图片技能生成1:1 favicon与真实图片Logo。Logo优先符合品牌行业/网站定位的特色字体字标，左侧尽量不附加icon；透明背景、无额外边距，不能以普通HTML文字或降低整图opacity假装透明图片。favicon独立方形设计，生成正式PNG并在所有页面head用link rel="icon"引用，必要时用清晰的品牌字母/简化标记，不把favicon再拼到字标Logo左侧。

每张Banner/About配图先明确本张的主题、内容侧重点、主体和与其他图片的差异，再生图。主视觉元素尽量位于视觉中心；Banner关键主体/叙事元素的实际呈现区域必须落在网站max-content版心内，先按PC/移动可见区域与裁切计算安全区，不把重要内容贴在全幅图片最边缘。Logo、标题与CTA也不能覆盖图片主体。完整新站优先选择支持多张图片的轮播模板，通常准备2–3张不同主题的Banner并填入模板实际幻灯片槽位；用户指定单Banner时遵从其范围。不得将所有轮播槽位都填成同一张图。多张Banner必须有不同内容与构图，About不得复用Banner同一张图；不能靠同图换裁切/滤镜/文件名冒充多张独立图片。只在同一张图适配多端时允许复用原图裁切。

首页选额外板块前，先读所选Header实际代码，检查是否已包含分类导航/分类套件、分类网格或可展开分类入口；若已具备，不再为凑额外板块重复选择独立分类板块，改用品牌故事、使用场景、编辑专题、特色内容或其他适合模板。功能相同的入口也算重复，不能仅换标题。页头分类链接本身仍指向真实Shop筛选结果，不能为去重破坏导航。

## 全站Toast与蒙层关闭

每个HTML页面（首页、交易、账户、正文、政策等）都必须注入唯一toast-component和components/toast.js，注册全局window.Toast，禁止业务通知调用浏览器alert或把alert别名当Toast。网站工具在write/finish时对完整HTML自动装配组件脚本和唯一实例，并创建缺失的components/toast.js，嵌套页面使用正确相对路径；已有实现保留时必须核对下述API。仅写文件绕过工具时也须执行finish。Toast脚本在app.js/账户组件业务执行前加载，API可在DOM就绪前接收消息。

全站统一调用Toast.show(message,{type,duration})、Toast.success/error/info/warning(message,options)、Toast.dismiss(id)、Toast.clear()；show返回id，duration:0表示保持至手动关闭。文案按目标语言输出；window.uiMessages.close提供本地化关闭文案，window.uiStyles.toast/toastClose定义统一控件样式。Toast通过安全文本或严格转义后的template渲染外部消息，支持可访问状态、手动关闭、超时消失，避免重复实例和阻挡页面交互。表单字段错误仍可内联展示，不能把长政策正文塞进Toast。未登录操作先Toast.info提示，不使用alert；加购/收藏等操作按通用规则跳登录，订单/结算页必须按入口守卫提示后跳首页。默认守卫留约900ms展示提示，业务不得多次提交或重复跳转。

所有有蒙层的弹窗、购物车/筛选/移动菜单抽屉，点击蒙层空白或装饰区域必须关闭对应浮层；点击面板、输入框或内容不得误关。此处仅为提示词/开发规范，不定义、不注入window.Overlay、统一data-overlay协议或全局点击/Esc拦截。每个组件在自身作用域内实现关闭按钮、蒙层点击、Esc与清理逻辑，关闭时移除自身open状态，恢复滚动、焦点和aria，重连不重复监听、断开解除事件。逐个验证浮层，不猜测所有fixed/深色元素是蒙层。

## 页面规范补充

Toast遵循用户标准目录中的components/toast.js，按WebComponent规范实现：命名ToastComponent、继承HTMLElement、Light DOM、template(data)/refresh()、唯一注册toast-component；状态、计时器和DOM事件由组件自身持有，connectedCallback幂等绑定，disconnectedCallback解除监听并清除计时器，重连可正常恢复。window.Toast只是调用组件的全局薄门面，不在全局函数里直接管理组件DOM或夹带弹窗统一接口。已有用户实现先读再复用，不覆盖用户文件。

### Logo 尺寸与留白（硬约束）

Logo 图片与其专用链接/包装容器的左右 margin、padding 必须为 0，禁止新增水平空槽、占位列或装饰留白，也不能通过给 Logo 图片添加 px/mx 变相缩小品牌标识。保留原始宽高比与 `object-fit: cover; display: block`，不切换为 contain，不同时强制宽高导致拉伸。源图片本身不能有左右透明空边，需在素材阶段去除，不能靠额外容器边距补偿。此明确要求优先于模板中的 Logo 装饰性边距，但不改变其他区域的导航间距与移动端安全边距。

* **PC端**：Logo 与同一页头主行中的导航、搜索/操作控件保持协调一致的显示高度，图片使用 `height: 100%; width: auto`，对应 `block h-full w-auto object-cover p-0 m-0`。Logo 链接与槽位继承该主行的有效内容高度，父级须有可解析的高度（优先 REM），避免 `h-full` 的祖先均为 auto 而实际失效。不能按包含公告条/第二导航行的整个 Header 高度放大 Logo，也不能再用桌面 `w-full h-auto` 覆盖此规则。不改变原模板断点、区域顺序及网格。
* **移动端及未进入PC布局的尺寸**：沿用 `width: 100%; height: auto`，对应 `block w-full h-auto object-cover p-0 m-0`，占满模板原有 Logo 槽位，不占满整个页头。通过模板实际PC断点切换两种模式，不自行新建冲突断点。

在375/768/1280px读回 Logo 图片及其专用容器的 computed style 与边界尺寸：两侧 margin/padding 为0；PC图片高度匹配有效槽位/同排控件高度、宽度按自然比例自适应；移动布局宽度匹配槽位、高度按自然比例自适应；无透明空边。不能只确认 class 字符串存在。

### REM 单位与页面最小高度（代码规范）

* 字号、间距、宽高、圆角等可缩放尺寸优先用 REM，优先选择 Tailwind 默认 REM 工具类；自定义尺寸使用如 `max-w-[11.25rem]`，避免写成 `max-w-[180px]`。Tailwind 的 `px-4` 是水平 padding 工具类，不代表使用 PX 单位，无需因此删除。百分比、fr、auto、vh 等用于相对布局时保留；细边框/发丝线可保留1px，素材原生像素、截图视口和浏览器测量值不必转为REM。换算需结合实际根字号，保留既有移动端12px/桌面16px规则，不靠改变根字号或模板断点掩盖尺寸问题。
* **每个完整HTML页面的可见整体高度不得低于100vh**，包括首页、登录/注册、空订单、空购物车和政策等短内容页。使用 `body` 或唯一页面外壳 `min-height: 100vh`（Tailwind `min-h-screen`），不能写固定 `height: 100vh` 截断长内容。页头、主体、页脚位于同一纵向 flex 外壳，主体 `flex: 1`，短内容时页脚落在视口底部，长内容正常滚动；不要给每个板块或页头/页脚之外的主体再重复加100vh，制造多余滚动。移动端可补充动态视口适配，但须保留不低于100vh的下限。
* 生成后检查代表性自定义尺寸实际使用REM；在375/768/1280px验证短页整体高度至少等于视口高度，长页内容完整可达且无固定高度裁切，再检查PC Logo与相邻控件高度及自然宽高比。

所有字体与第三方库继续用在线HTTPS CDN，但避免jsDelivr/jsdeliver（含cdn.jsdelivr.net、fastly.jsdelivr.net、gcore.jsdelivr.net等镜像/别名），优先可用的cdnjs、Google Fonts或库官方CDN；项目有既定依赖版本就保留版本，不因为换CDN静默升级。

PC在统一最大内容宽度max-content内，Header Logo与导航、主视觉文案、商品网格、各板块及Footer内容的左右边缘尽量对齐。桌面外层容器优先无额外水平padding，避免父容器已有版心后又在子容器叠加px/mx；Logo链接/容器尽量p-0 m-0、图片去除透明留白，左右不人为留空槽。保留正常导航间距、卡片/控件内部可读间距与移动端安全边距，不取消PC最大宽度，也不把所有窄表单硬撑满版。此明确要求优先于旧模板的装饰性边距，但保留区域、列数、图片比例和断点。

单页业务逻辑（Shop筛选/排序/分页，详情tab/折叠/评论分页，登录表单等）写进对应HTML的script标签，通常放依赖和组件之后；不再为此创建js/pages/*.js、shop.js、product.js等单页逻辑文件。js/app.js只保留全站配置/共享初始化，SDK和复用WebComponents仍可独立文件；不要把单页代码塞到app.js污染全站。已有用户文件不擅自删除，修改时按授权范围迁入页面script并同步移除对应引用。

商品详情的介绍/规格/评论过长时，依据选定布局使用折叠/展开、分页、分批加载或合适的标签页展示，避免整页被长内容无限拉长。保留完整数据与可达入口，不简单截断丢弃、不把溢出内容永久隐藏；展开/分页按钮有清晰文案、键盘支持与aria状态，移动端也可操作，切换商品/排序后重置正确位置和页码。单页逻辑内联，数据查询仍走SDK。

## 商品渲染与分类字段

导入商品的main_image/images保留源相对路径；卡片、详情图库、分类图、购物车展示等在设置img.src、srcset、background-image或HTML图片属性时，显式调用storeData.imageUrl(path)（或productImageUrl(path)）得到CDN URL，并按上下文安全转义。不修改productData/SDK返回对象，不在导入阶段批量替换图片地址，也不安装全局拦截自动改图。绝对HTTP(S)地址保持可用，原始JSON绝不写回。

源品类>6时必须进行有意义的二次归类，不能机械取前5类+More。website_products先返回源分类摘要；如返回classification_required，就根据摘要整理覆盖全部源类的category_map，再调用导入。摘要分页用category_offset/category_limit和category_page.next_offset读取，不能直接读取原JSON。成功后SDK.get/list/filter/categories返回的category必须是二次归类，source_category仅保留来源追溯；分类菜单与Shop筛选统一读SDK.categories()，不重新展示原分类。通常5–6主类，源信息不足时使用真实可用类别并说明，不造空类。
